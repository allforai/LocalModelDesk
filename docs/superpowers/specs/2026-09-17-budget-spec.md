# 模块 spec：budget（资源预算与上下文管理）

**单一职责** 「这台机器此刻还装得下什么」的唯一权威。
能力必须从**这台机器的实测**里长出来，不从写死的常数里来。

## 背景约束

本地模型产品的核心价值是资源管理。现有 `arbiter` 把「资源永远不够」当成公理：
三者互斥、媒体在跑就拒绝、开媒体先全卸。这套假定在 36GB 机器上成立，
在 186GB 上偏保守，在 512GB 上是错的——那台机器完全能同时驻留聊天模型与媒体模型。

同时存在三个洞：

1. 没有任何需求描述「这台机器能做什么」，只有「不能做什么」。
2. R-arbiter-07 只管加载那一瞬间；会话中 KV cache 长出来的内存无人负责。
3. 媒体作业峰值**已有按参数估算**（`desk/media/memory_estimate.py`，
   由 `media/service.py:104` 传入 `can_start_heavy`），但它的标定常数
   （草稿档 27.0 GiB、每单位体积 1.4 GiB）是 2026-09-08 在**一台机器上**
   量出来写死的，不随机器变化，也不会被后续运行修正。

聊天侧则完全没有上下文管理：每轮把全部历史原样发送，无截断、无压缩、无上限。

本项目尚未发布，不存在需要兼容的存量行为。

## 需求

- **R-budget-01** 每个额度必须标注来源 `predicted` / `measured` / `unavailable`，
  在台面状态对象与诊断输出中可见。预测与实测不可混为一谈。

- **R-budget-02** 模型声明窗口按序读取：`text_config.max_position_embeddings` →
  顶层 `max_position_embeddings` → 记 `unavailable`。**禁止读取 `vision_config`**。
  三条顺序不得调整，不得回落成默认值。

- **R-budget-03** 冷启动额度由 `config.json` 推算（每 token 字节）与内存快照合成，
  并据此向 mlx-lm 传入 `--prompt-cache-bytes` 与 `--prompt-cache-size`。
  不传限额等于无上限，是当前的缺陷。

- **R-budget-04** 自校准：每轮完成后，由 mlx-lm 日志的 `Prompt Cache` 字节数除以
  该轮 `usage.prompt_tokens`，得出本机该模型的实测每 token 字节，写入实测档案。
  档案条目须记录权重大小，与 `ModelEntry.gb` 不符即作废重测。

- **R-budget-05** 修正的两个生效点必须区分：软触发（压缩阈值）立即生效；
  硬边界（`--prompt-cache-bytes`）下次加载生效。二者不得混淆。

- **R-budget-06** 保留 `memory_estimate.estimate_bytes(kind, params)` 的按参数估算形式——
  按作业种类给一个数会让不同分辨率的作业共用同一个估值，这是它当初就修掉的缺陷。
  新增的是**标定来源**：每次媒体作业运行期采样 `available_bytes`（启动前基线、
  运行中最低点、结束差值）得到本机实测峰值，写入实测档案，用于修正该公式的常数项。
  本机尚无实测记录时，沿用代码内写死的 2026-09-08 标定值，并标 `predicted`。

- **R-budget-07** 重活能否并存由预算判定，预算不足时结果即互斥。
  判定的输入是**一组**重活而非一对：`fits(workloads)`。三件能否共存不等于
  三个两两判断的合取，「最小让出」也只有在集合上才算得出来。
  拒绝必须带机器可读原因与数字：需要多少、现有多少、依据来源为预测还是实测。

- **R-budget-10** 一组重活的依据来源取其中最弱者：只要有一件是 `unavailable`，
  整组按 `unavailable` 处理并走保守路径。不得让「两件实测加一件未量过」
  被当作实测依据放行。

- **R-budget-08** 预算判定「装得下」而实际触发内存压力时，该次失败必须落盘，
  并永久收紧该组合的预算。系统必须从失败中学习，不只从成功中学习。

- **R-budget-09** 内存压力升高时的第一动作是令 mlx-lm trim KV 缓存，
  而非卸载模型或终止媒体作业。压力传感器是兜底闸，不是决策者。

- **R-context-01** 会话发送给模型的内容受预算约束：超过 `Budget.for_chat()` 给出的
  触发点时，较早消息由一条结构化摘要替代，尾部若干轮保持原文。
  保留轮数由预算反推（尾部与摘要之和不超过触发点的一半，且至少保留最近一轮完整问答），
  不得写死为常数——各模型每 token 开销相差一个数量级。

- **R-context-02** 摘要按固定模板填写，模板含且至少含：用户原始意图、关键概念、
  涉及文件与代码、错误与修法、**用户历次发言逐条列出**、待办与当前工作。
  不得使用开放式「总结一下」指令。

- **R-context-03** 压缩只影响发送内容，不影响存储与展示。会话文件保留全部原始消息，
  用户在界面上始终可以看到每一条。

- **R-context-04** 压缩在两轮之间进行，使用当前驻留模型，不加载第二个模型。
  压缩过程对用户可见（明确的进行中提示），不得静默阻塞。

- **R-context-05** 摘要作为一条 `role: "summary"` 的会话消息存在，记录其替换的消息区间，
  可被用户编辑，亦可在原文基础上重新生成。

## 对 arbiter 现有需求的改写

- **R-arbiter-01** 改：重活能否并存由预算判定；预算不足时退化为互斥。持有者由单个变为一组。
- **R-arbiter-04** 改：拒绝条件由「媒体在跑」变为「预算装不下」。
- **R-arbiter-05** 改：仅在预算不足时让出，且最小让出。
- **R-arbiter-07** 改：由加载时一次性检查，变为持续生效。
- **R-arbiter-02 / 03 / 06** 不变。

## 非目标

- 不做工具调用、不做 skill 机制、不做 websearch。这三项另行立项；
  其中 websearch 与 README「不上云、推理不出门」的定位存在冲突，需先行裁决。
- 不在本模块内实现压缩算法之外的对话质量优化。
- 不为非 macOS 平台设计内存探测。
- 不猜测 mlx 内部的 KV cache dtype 与分页策略——该常数由实测得出，不由推断得出。

## 验收

每条需求都须有对应测试，且每条测试都须验证「被测行为失效时它会失败」：
短接实现后必须变红，双向行为须双向验证。绿色若从未被观察到能变红，不构成证据。
